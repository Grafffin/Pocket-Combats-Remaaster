# Серверная правда: перенос экономики и наград на сервер

Статус: план, 2026-10-24. Цель: игрок не может нарисовать себе золото, вещи, опыт, здоровье, награды боя и лут.

## 1. Что сейчас

- Герой (`characters.data`) и сундук (`characters.stash`) целиком собирает клиент и сохраняет через `update` (`cloud.js`). Защита только грубая: лимиты скорости роста уровня и золота (`0007_protection.sql`). Любую вещь, золото, материалы, очки умений можно вписать в консоли.
- Рынок (`0012_market.sql`) уже атомарный на сервере, но продаёт то, что лежит в клиентском герое, поэтому нарисованная вещь продаётся.
- Бой детерминирован (`engine.js`, `makeRng(seed)`), но seed, монстр, герой-боец (`toFighter`), число зелий и итог (`applyBattleResult`) клиентские. В общем бою считает хозяин, участники воспроизводят его события (`lockstep.js`), то есть хозяин-читер может прислать любые события.
- Вся игровая логика (`data.js` … `world.js`) без DOM и уже работает в Node (тесты). `world.js` специально считает мир от времени `now`, «чтобы сервер мог считать то же самое».

## 2. Решение

**Supabase Edge Function `game` (Deno) исполняет те же файлы `web/battle/js/*.js`, что и клиент.** Переписывать логику на SQL нельзя: сервер должен воспроизводить бой с той же последовательностью случайных чисел, включая фразы лога, а это возможно только тем же кодом.

- Клиент шлёт только намерения: `{ op, args, rev, v }` (купить, перековать, напасть, итог боя с журналом ходов).
- Функция: проверяет JWT игрока, сверяет версию сборки `v` с своей (та же `version.js`, иначе ответ `version` и клиент перезагружается), блокирует строку `characters` (`select … for update` через RPC с сервисным ключом), сверяет `rev`, применяет ту же функцию из `economy.js` / `items.js` / `progression.js` с **серверным** `rng` и **серверным** временем, сохраняет, возвращает `{ char, stash, rev, result }`. Клиент делает `app.adoptChar` (как уже сделано для рынка).
- Писать в `characters` может только функция (сервисный ключ доступен внутри Edge Function автоматически, пользователю его давать не нужно). У `authenticated` права `insert/update` на `characters` забираются в последнем этапе.
- Бой: сервер выдаёт seed, монстра и снимок бойца при начале, а при конце **сам переигрывает журнал** событий движком и сам начисляет опыт, золото, лут, расход зелий. Клиент показывает бой как сейчас (без задержек между ходами), сервер участвует только в начале и в конце.
- Общий бой: снимок бойца каждого участника пишет сервер при вступлении (`battle_members.tpl`), хозяин берёт seed и снимки с сервера. В конце любой участник сдаёт журнал, сервер один раз переигрывает его, сверяет отпечаток `cs` и делит награду по вкладу (`rewardMult`). Подделанный журнал не сходится с переигровкой и награды не даёт. Lockstep-протокол не меняется, тесты `lockstep-test` и `lockstep-stress` остаются зелёными на каждом этапе.
- Версия: функция деплоится тем же коммитом, что и Pages (`pages.yml`), с той же строкой версии. Окно рассинхрона (Pages обновился раньше функции или наоборот) закрывается ответом `version` и одной перезагрузкой, как в общем бою.
- Офлайн-игра без входа отключается: прогресс есть только у вошедших (гостевой вход остаётся).

Цена: каждое действие героя — один вызов функции (~100–300 мс). Бесплатный тариф даёт 500 тыс. вызовов в месяц, для текущей аудитории с запасом.

## 3. Этапы (каждый — свой PR)

| # | Что | Миграция | Риск для общих боёв |
|---|---|---|---|
| 1 | Каркас: `supabase/functions/game` грузит игровые JS, проверка JWT и версии, блокировка героя + `rev`, операция `ping`/`load`; деплой из `pages.yml`; локальный тест функции в Node | `0013_game_core.sql`: `game_lock`/`game_commit` (только service_role) | нет |
| 2 | Создание героя и действия вне боя: лавка, скупщик, алхимия, эликсиры, разбор, кузница (заточка, перековки, крафт), надеть/снять/замок, сундук, характеристики, умения, слоты, настройки, сложность | — | нет |
| 3 | Мир: переходы, передышка, выбор и занятие монстра считает сервер по своему времени | — | нет |
| 4 | Одиночный бой: `battle_start` (seed, монстр, снимок бойца) и `battle_finish` (журнал → переигровка → награда) | `0014`: таблица выданных боёв | нет (одиночный путь) |
| 5 | Общий бой: снимки участников с сервера, награда по переигровке журнала хозяина | `0015`: `battle_members.tpl`, кэш итога | да: новый тест переигровки + оба lockstep-теста + e2e-coop |
| 6 | Замок: забрать у клиента запись в `characters`, убрать лимиты-костыли, клиент без входа не играет, рынок продаёт только серверные вещи | `0016_lockdown.sql` | нет |

До этапа 6 старый путь сохранения работает параллельно, поэтому каждый этап можно выкатить и откатить отдельно, игра не ломается между этапами.

## 3а. Как сделано (2026-10-24)

- Этапы 3–5 объединены: в сети любой бой идёт через lockstep, поэтому отдельного одиночного пути нет. Сервер выдаёт бой (`fightStart`: монстр по своему миру и времени, seed, снимок бойца, запись в `game_fights`), вступающий получает свой снимок (`fightJoin`), в конце каждый сдаёт историю боя (`fightEnd`), сервер сверяет seed, монстра и снимки, переигрывает и начисляет награду. Слишком быстрый бой (ходов больше, чем прошло тиков) и подделанная история награды не дают. Выпитые зелья списываются из текущего запаса.
- Переходы (`travel`, `cancelTravel`, `arrive`) считает сервер, уйти посреди боя нельзя.
- Пока миграция 0013 не применена, функция отвечает `fights: false` и бои считаются по-старому.
- Проверки: `server-test.js` (подделки, доли, зелья, бегство), `SERVER=1 e2e-coop.js` (весь сквозной сценарий общего боя с подставной функцией).

- Замок (последний этап): когда функция отвечает и бои на сервере (`cloud.locked`), клиент вообще не пишет `characters`: локальная копия — кэш, при входе берётся серверный герой (офлайн-герой уходит в резервную копию `pc-cloud-backup-v1`). Миграция 0014 забирает у `authenticated` право писать героя. Офлайн-игра без входа осталась, но в аккаунт больше не переносится.

- Задержка действий (2026-10-24): действие без случайности и времени (надеть, снять, замок, сортировка, сундук, лавка, продажа, характеристики, умения, настройки) клиент сначала прогоняет сам на копии героя (`predict` в `hub.js`: обращение к `ctx.rng/now`, `Date.now`, `Math.random` — значит, ждём сервер) и сразу показывает итог, а сервер подтверждает в фоне; при отказе клиент берёт серверного героя (`cloud.act(op, args, true)`). Кузница, крафт, бои и переходы по-прежнему ждут ответ. Функция помнит проверенный токен 5 минут (не ходит в auth на каждое действие), герой и запись боя читаются параллельно, при возврате во вкладку функция будится `ping`.

## 4. Что нужно от владельца

- Один раз: токен доступа Supabase (Account → Access Tokens) в секрет репозитория `SUPABASE_ACCESS_TOKEN`, чтобы GitHub Actions сам деплоил функцию. Без него каждое обновление функции придётся вставлять вручную в редакторе Edge Functions.
- Применять миграции 0013–0016 в SQL Editor, как раньше.
