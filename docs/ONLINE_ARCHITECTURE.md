# Онлайн: проект архитектуры

Статус: проект, кода нет. Решения владельца приняты 2026-10-23 (см. §9).

## 1. Исходные условия

- Клиент статический (`web/battle/`, чистый JS, без сборки), живёт на GitHub Pages. Сервера нет.
- Движок боя (`engine.js`, `items.js`, `progression.js`, `world.js`) не зависит от DOM и работает в Node. Это главное преимущество: ту же логику можно запускать на сервере.
- Сейчас герой лежит в `localStorage` (`pc-character-v3`), склад в `pc-stash`.
- Нужно: регистрация и вход, БД, сохранение прогресса, список игроков на локации, выдвижной чат, вкладка «Бои» на локации («кто с кем дерётся»), вход в чужие бои, до 10 человек в одном бою.
- Ограничение: бесплатный тариф, регистрацию и ключи делает владелец.

## 2. Сравнение вариантов бэкенда

| | Supabase | Firebase | Свой сервер (VPS / Render / Fly) |
|---|---|---|---|
| БД | Postgres, SQL, RLS | Firestore (документы) | любая (Postgres/SQLite) |
| Авторизация | email, OAuth, анонимный вход, готово | email, OAuth, анонимный вход, готово | писать самим (пароли, сессии, сброс) |
| Realtime | Presence, Broadcast, подписки на изменения таблиц | подписки на документы, Realtime DB | WebSocket, писать самим |
| Серверная логика | Edge Functions (Deno), RPC в SQL | Cloud Functions (нужен платный план Blaze) | любая, полный контроль |
| Бесплатный тариф | 500 МБ БД, 50 тыс. активных в месяц, 200 одновременных realtime-соединений, проект засыпает после недели простоя | щедрый, но функции требуют карту | Render free засыпает и холодно стартует; Fly и VPS требуют карту |
| Совместимость с Pages | да, клиент `supabase-js` с CDN, без сборки | да | да, но нужен CORS и свой домен/TLS |
| Риск | лимит 200 соединений | счёт растёт с чтением документов; сложные запросы неудобны | вся эксплуатация на владельце |

Вывод: для игры с реляционными данными (персонажи, вещи, бои, участники) и без сборки на клиенте Supabase подходит лучше. Firebase неудобен для связей и серверной проверки (функции платные). Свой сервер даёт полный контроль над боем, но требует эксплуатации и писать авторизацию с нуля.

## 3. Рекомендация

**Supabase (Postgres + Auth + Realtime + Edge Functions).** Причины: ноль серверов для поддержки, готовая авторизация, Presence и Broadcast закрывают список игроков и чат, а Edge Functions на Deno могут импортировать тот же `engine.js`, поэтому бой считается один раз на сервере и клиенты только показывают результат.

Путь отхода: схема в чистом Postgres, логика боя в общем JS. Если лимиты станут тесны, переезд на свой сервер с Postgres и WebSocket не потребует переписывать движок.

Принцип: **клиент не авторитетен**. Ввод только «намерения» (атаковать, умение), результат считает сервер. Но переход на серверный авторитет делаем поэтапно (см. §8), чтобы не заморозить игру на месяц.

## 4. Схема БД (Postgres)

Все таблицы с включённой RLS. Игрок читает общее и пишет только своё; боевые изменения идут только через Edge Functions с сервисным ключом.

```
profiles        id uuid PK = auth.users.id, nick text unique, created_at, last_seen
characters      id uuid PK, user_id → profiles, class, level, exp, gold,
                data jsonb          -- то же, что pc-character-v3 (версия в data.v)
                version int         -- CHAR_VERSION, для миграций
                location_id text   -- где сейчас; для списка игроков
                updated_at
stash           user_id PK, data jsonb   -- склад аккаунта (300 ячеек)
locations_state location_id PK, tick bigint, monsters jsonb   -- пул монстров (общий)
battles         id uuid PK, location_id, monster_ref jsonb, state jsonb,
                status (open|running|won|lost), max_players int default 10,
                started_at, tick_no, created_by
battle_members  battle_id → battles, character_id → characters, side,
                joined_at, left_at, hp, alive bool, PK(battle_id, character_id)
battle_actions  id, battle_id, character_id, tick_no, action jsonb, created_at
chat_messages   id bigserial, channel text (loc:<id> | global), user_id, nick,
                body text (<=300), created_at   -- хранить последние ~200 на канал
```

Присутствие игроков и «печатает…» не хранятся в таблицах: используется Realtime Presence.

Замечание: `characters.data` — jsonb с существующей структурой, а не разложенные колонки. Миграции остаются в `progression.js`, схема БД не меняется при каждом новом поле.

## 5. Авторизация

- Supabase Auth: email + пароль (регистрация с подтверждением можно отключить на старте), позже Google/Discord.
- Гостевой режим: анонимный вход Supabase, чтобы можно было играть сразу; позже привязать email и сохранить прогресс.
- Триггер на `auth.users` создаёт `profiles` (ник уникальный, проверка длины и мата — простая).
- Сессия хранится библиотекой в `localStorage`; JWT идёт во все запросы, RLS опирается на `auth.uid()`.
- Публичный ключ (`anon key`) лежит в клиенте, это нормально; секретный `service_role` только в Edge Functions.

## 6. Сохранение прогресса

1. При входе: если есть серверный персонаж, он главный; если нет, а в `localStorage` есть герой, предлагаем «загрузить локального героя в аккаунт» (разовый импорт).
2. Автосохранение: после значимых событий (бой окончен, покупка, заточка, смена экипировки) и раз в 30–60 с при изменении. Запись `characters.data` с `updated_at`; клиент хранит копию в `localStorage` как офлайн-буфер.
3. Конфликты: сравнение `updated_at`/ревизии; при расхождении побеждает серверный, локальный предлагается как отдельный слот (защита от потери).
4. Защита от подделки (поэтапно): сначала проверка границ на сервере (уровень, золото растут не быстрее порога за время), потом перенос наград боя на сервер (§7.4), потом вещи и экономика.

## 7. Онлайн-механики

### 7.1 Присутствие на локации
Realtime Presence, канал `loc:<id>`. Клиент при входе в локацию делает `track({id, nick, level, class, busy})`, при выходе `untrack`. Список «Игроки здесь» внизу экрана локации строится из `presenceState`. Не пишем в БД, нагрузка минимальна. Лимит: показываем первые 50 и счётчик.

### 7.2 Чат
- Выдвижная панель (как в оригинале): вкладки «Локация», «Общий». Новые сообщения без панели дают бейдж-счётчик.
- Отправка: Edge Function или вставка в `chat_messages` с RLS (только своим user_id, длина ≤ 300, ограничение частоты 1 сообщение в 1.5 с через функцию).
- Доставка: Realtime Broadcast на канал + запись в таблицу; при открытии подгружается последние 50.
- Модерация на старте: ограничение частоты и жалоба; бан по `profiles.banned`.

### 7.3 Список боёв на локации
Новая вкладка на экране локации под монстрами: «Бои». Строка: `Игрок А, Игрок Б → Монстр (ур.) · 3/10 · вступить`. Источник: `battles` с `status in (open, running)` по `location_id`, подписка на изменения (Realtime postgres_changes) с фильтром по локации. Бой виден, пока в нём есть живые участники, или N секунд после конца.

### 7.4 Совместные бои до 10 человек
- Бой создаётся, когда игрок нападает на монстра: запись в `battles`, монстр помечается занятым в `locations_state` (замена клиентского `busySince`).
- Вступление: RPC `join_battle(battle_id)` атомарно проверяет `count(members) < max_players`, локацию, свободен ли игрок, и добавляет участника. Конкуренция решается транзакцией (`SELECT ... FOR UPDATE`).
- Ход: тик остаётся 10 с. Игроки отправляют действие в `battle_actions` (через Edge Function). Edge Function по таймеру тика (pg_cron или ленивое вычисление: первый запрос после окончания тика закрывает его) собирает действия, прогоняет общий `engine.js` и пишет новое `state`. Клиенты получают состояние через Realtime.
- Масштаб монстра: здоровье и атака растут с числом участников (в духе `poolSize`: +N% за игрока), награда делится по вкладу (урон/лечение), чтобы не было «халявы» для зашедшего на секунду (минимальный вклад для награды).
- Цель монстра: сначала по агро (последний атаковавший), потом случайная среди живых, чтобы бой из 10 не был скучен.
- Награды (опыт, золото, дроп) выдаёт сервер при завершении боя, поэтому подделать их с клиента нельзя.
- Выход из боя: выбывание = поражение для этого игрока, бой продолжается; бой без живых участников закрывается.

## 8. Разбивка на подзадачи (каждая — один PR)

Порядок важен: каждая следующая опирается на предыдущую.

1. **Основа Supabase и вход.** Подключение `supabase-js`, файл конфигурации (ключ публичный), экран входа/регистрации/гостя, `profiles` с триггером, миграции SQL в `supabase/migrations/`. Без изменения игры: можно играть как раньше.
2. **Сохранение героя в облаке.** `characters`/`stash`, импорт локального героя, автосохранение, разрешение конфликтов, офлайн-буфер. Миграции остаются в `progression.js`.
3. **Присутствие и список игроков.** Presence по локациям, блок «Игроки здесь», смена локации обновляет `characters.location_id`. Вёрстка 375×812.
4. ✅ **Чат.** Выдвижная панель, вкладки локация/общий, таблица `chat_messages`, ограничение частоты, бейдж непрочитанного.
5. ✅ **Список боёв (общий мир — позже).** `locations_state` вместо клиентского пула, `battles`/`battle_members`, вкладка «Бои» на локации, создание боя (один игрок), кто с кем дерётся. Пока бой считает клиент создателя.
6. **Совместные бои до 10 (часть 1 ✅: общий запас здоровья монстра, `join_battle`/`battle_hit`, миграция 0005; часть 2 ✅: общий мир монстров `world_mobs`, миграция 0006).** `join_battle`, `battle_actions`, серверный расчёт тика через Edge Function с общим `engine.js`, масштаб монстра, доля наград. Включить для всех боёв.
7. **Защита и стабилизация (часть 1 ✅: миграция 0007 — границы прогресса, лимиты боя/чата/боёв; жалобы/бан и нагрузочный тест — позже).** Серверная проверка наград и границ прогресса, антиспам, жалобы/бан, лимиты free tier (мониторинг соединений), нагрузочный тест симулятором ботов.

Каждая подзадача описывается отдельно в своём PR; перенос расчёта боя на сервер (шаги 5–6) самый рискованный, поэтому до него игра остаётся работоспособной и без него.

## 10. Риски

- **Лимиты free tier:** 200 одновременных realtime-соединений и засыпание проекта после недели простоя. Для закрытого теста достаточно; при росте нужен платный тариф (≈25 $/мес) или свой сервер.
- **Чит с клиента:** пока награды считает клиент, героя можно подделать. Закрывается шагами 6–7; до этого онлайн считается «доверенным».
- **Задержка:** тик 10 с мягко переносит сетевые задержки, поэтому игровой темп с realtime совместим.
- **Edge Functions и общий движок:** `engine.js` нужно держать совместимым с Deno (классические скрипты в `PC`); потребуется тонкая обёртка-загрузчик, это отдельная часть шага 6.
